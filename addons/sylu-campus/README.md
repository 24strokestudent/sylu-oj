# sylu-campus（V1 不启用）

对应实施计划 §12 §53 §54。

**这里只有设计说明，没有可加载的插件代码。** 没有 `package.json`，也就不可能被 `hydrooj addon add` 误装成一个"看起来能用但没反应"的功能（§65）。

## 为什么现在不做

计划明确要求：V1 先用 Hydro 普通账号跑通**注册 → 登录 → 刷题 → 作业**全链路，
等核心稳定以后（Phase 9 之后）再做校内身份扩展。

第一阶段不阻塞上线：

```text
学生注册 Hydro 普通账号  →  即可刷题
```

## 将来要做什么

```text
addons/sylu-campus
├─ 学号绑定
├─ 学生验证状态
├─ 班级信息
├─ 教师身份标识
└─ 校内公告
```

### 硬性边界

1. **不修改 Hydro Core User Model。** 通过 Addon 增加独立集合与接口，用户表只加外挂关联（§53）。
2. **禁止保存教务密码。** 用户主动验证 → 验证成功后只落盘：

   ```text
   student_id
   verified_at
   ```

   服务器**不得长期保存**教务用户名与密码（§54）。这一点比功能本身重要。
3. 教务系统接入必须由用户主动触发验证，不做后台批量代登录。
4. 对外暴露数据一律走 Addon 的受控 API（认证 / 权限 / 限流 / 字段过滤），
   其他系统（如 SYLUlive）**禁止直连 Hydro MongoDB**（§55 §56）。

## 与现在的代码如何共存

现在的替代方案是 Hydro 原生能力，够用就不要提前造：

| 将来 sylu-campus 的功能 | V1 先用什么 |
|---|---|
| 班级管理 | Hydro 域内**用户组**：`2026-c-01`、`2026-datastructure-01`（§13） |
| 教师身份 | 管理员人工授予 Teacher 权限 / 域权限（§11） |
| 学号 | 用户名规范（如 `2403060128`），或注册后由管理员批量导入 |
| 校内公告 | Hydro 原生公告 + `ui-default.footer_extra_html` |
